# Tasks — M1, walking skeleton

## Convenções desta entrega

**Nível de assistência: `high`** (default; o usuário não especificou). Toda task termina com `(owner: agent)` ou `(owner: human)`. `owner: human` só onde a régua do `high` exige: coisa fora do repositório que só o usuário faz (token real, push, arquivar), ou julgamento que teste não checa (texto do README, ponta a ponta com o bot real). Todo o resto é `agent`.

**Commits.** Conventional Commits com escopo, corpo em português, e a linha de atribuição ao fim de **toda** mensagem:

```
Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
```

Os textos abaixo são a **primeira linha**; a atribuição é obrigatória e não é repetida.

**Toolchain Go fora do `PATH`.** Antes de qualquer `go`, `sqlc` ou `staticcheck` avulso: `export PATH=/usr/local/go/bin:$HOME/go/bin:$PATH`. `make <alvo>` já faz isso internamente. O `~/.zshrc` do usuário não é tocado.

**Docker é necessário** para os testes de banco (testcontainers). `go test -short ./...` os pula; a verificação de cada task diz quando `-short` **não** basta.

**Segredos.** O `.env` da raiz contém o token real do Telegram e a chave do Ollama. **Nenhuma task o lê, imprime ou cita.** Os testes usam tokens sentinela (`tok-sentinela-...`), nunca o real; tasks que precisam do token real descrevem o passo por nome de variável e são `owner: human`.

**TDD com vermelho visível.** Onde uma task diz "vermelho", o passo de verificação é rodar o teste **antes** da implementação e ver **falhar pelo motivo certo** (nomeado na task); só então implementar. Um teste que nunca foi visto falhando é decoração.

**Rastreabilidade.** Cada task cita a capability da spec delta que ela cumpre. Task que não remete a um requirement seria sinal de spec incompleta.

**Ordem é dependência real.** Seções 1 a 6 podem ser feitas em paralelo **entre si** só onde a task diz; a seção 7 depende de 2 a 6; a 0.1 é pré-requisito de *aplicar* (não de propor).

## Questões em aberto / riscos

O que segue em aberto de fato. A numeração original foi mantida para as referências cruzadas. **N = decisão dele; R = risco a vigiar.**

6. **N (antes do M3) — Perda de update se a persistência falhar.** O ACK do `go-telegram/bot` avança o offset **antes** do handler: se o banco estiver fora do ar, aquele update **se perde** (o Telegram o considera entregue); a fila de capacidade 1 limita a exposição num crash a ~2–3 updates, e o log de erro traz o `update_id`. *Recomendação: aceitar no M1* (o eco é descartável) e **decidir antes do M3**, quando um update perdido passa a ser uma ação perdida. Saídas futuras: controlar o offset manualmente, ou webhook com ACK **depois** da persistência. *Aceitação no M1: decidida (Decisões tomadas nº 7). Em aberto: a estratégia, a fixar antes do M3.*
9. **R — Um único token para dev (polling) e futura produção (webhook).** Polling e webhook ativos ao mesmo tempo dão `409`. O plano não chama `deleteWebhook` (derrubaria a produção). Quando existir produção, usar **outro bot** para desenvolvimento (decidido, Decisões tomadas nº 10).
10. **R — Docker Hub e o CI.** A primeira execução do CI puxa `postgres:16` e a imagem do *reaper* do testcontainers; limite de taxa anônimo é raro, mas possível. Não alterei `ci.yml`; se falhar, a task 9.2 diz o que reportar.
11. **R — Revisão humana do diff de redação (6.7).** As tasks de privacidade são verificáveis por máquina (marcador e token sentinela, `log` global capturado), então são `agent`; mas o classificador/redator é o caminho de segurança mais sensível do M1. O usuário **decidiu olhar esse diff antes do merge** (Decisões tomadas nº 11; nota na task 6.7); a task segue `agent` pela régua do `high`.
12. **R — Premissas não verificadas por mim** (nada foi executado; só li código e rodei `openspec validate`, `govulncheck` num módulo-amostra e `go mod` para as versões): (a) que o `sqlc` v1.31.1 gera bem `INSERT ... ON CONFLICT DO NOTHING RETURNING` com `:one` (o resultado sem linha vira `pgx.ErrNoRows`, comportamento conhecido, mas não rodei); (b) que `pgx.Tx.Begin` cria *savepoint* como o `testdb.Tx` supõe; (c) que `WithUpdatesChannelCap(1)` + `WithWorkers(1)` + `WithNotAsyncHandlers()` produzem exatamente o backpressure descrito (li o código de `getUpdates`, `waitUpdates` e `ProcessUpdate`, não executei); (d) as versões que o `go mod tidy` escolherá no repositório; (e) que o runner `ubuntu-latest` roda o *reaper* do testcontainers sem configuração.
